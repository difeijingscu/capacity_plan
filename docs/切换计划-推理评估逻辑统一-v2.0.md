# 切换计划：推理评估逻辑统一（目标版本 v2.0.0 / engine-v2.0.0）

> 制定时间：2026-11-12
> 前置调研：两轮代码级全量梳理（推理评估页 2571 行逐行解析 + 后端三池链路全量扫描），关键结论均经人工核验。
> 已确认决策：① 保留 React 业务场景页 + 后端移植引擎；② 移除 CV 与多模态；③ 芯片口径全以推理评估页为准；④ 本期不做自定义芯片。

---

## 0. 目标与范围

1. **业务场景页换引擎**：用「推理评估」页（`frontend/public/inference-eval.html`，自包含单页）的计算逻辑替换业务池现有计算链路（`engine/inference.py` 四约束引擎），完成业务场景算力规划功能。
2. **三池数据统一**：用推理评估页带来的新数据（8 张昇腾芯片、32 个模型、29 个场景档、新工程系数体系）替换后端 catalog，让**创新服务池、开发测试池**也切换到新数据（公式不变，数据源换）。

**不在本期范围**：推理评估 iframe 页本身保持自包含不动；自定义芯片登记；PD 分离形态；费用估算（cards.json 参考卡）不动。

## 1. 现状关键事实（已核实）

| 维度 | 推理评估页（新） | 后端现状（旧） | 差异结论 |
|---|---|---|---|
| 引擎 | A/B/C 三维约束取 max + M/G/1 排队 + roofline 混算；输出最小卡数（不含余量）；奇数补偶；8 卡/台 | 四约束链（A/B/C + SLA 回验加 DP + 混部抬升）+ TP×PP×EP×DP 拓扑枚举 + timing 经验拟合公式 | **两套不同公式**，需整体移植替换 |
| 模型 | 32 条（DeepSeek/Qwen/GLM/Kimi/MiniMax） | `inference_models.json` 32 条 | **100% 同源**（key 与数值完全一致），仅字段命名差异 |
| 芯片 | 8 张（910b/910b32/910c/950pr32/950pr/950dt36/950dt32/950dt），互联 196/392/1000 GB/s（灵衢口径），功耗板卡级 0.30~1.00 kW | 6 张，key 体系不同（`950(425T)` 等），互联 56/112 GB/s，功耗 0.65~2.2 kW | 分叉 2~9 倍；**以页面为准**；后端多参考价格字段（保留） |
| 场景 | 29 档 + 7 分组 + 每档默认模型 + 预置场景 | 6 档 | 页面是超集；**rag 并发 9→100、think 9→500 是实质性口径变化** |
| 工程系数 | ENG_DEFAULTS 按芯片 8 条（**910c: mfuP 0.26 / ratio 0.80**）+ ENG_CONST 6 常数 + TIERS 三档统一缩放（保守×0.8/均衡×1/激进×1.2，memUtil 半幅） | inference_params.json：sensitivity 三档向量缩放 + timing 24 项经验式 + aggregation margin 1.2；910c 0.36/0.58 | **两套代数**；910C 系数、时延模型、余量口径全部不同 |
| 精度 | 3 档：bf16 / w8a8 / w4a8（w4a8 需 nativeInt4） | 6+4 档枚举（auto/bf16/fp16/fp8/int8/int4 + KV 档） | 枚举需收敛 + 旧值迁移映射 |
| 创新/研发池 | —（页面无此概念） | llm-phases-v1 / lora-work-v1 公式，数据源 `models.json`（9+1 条，含 yolo CV、多模态图文） | **公式保留，数据源换**到 32 LLM；CV/多模态移除 |

**必须知道的既有铁律（继续有效）**：
- 卡数（物理台数）与算力（P，BF16 基准）不同量纲，不能相加比较；
- 余量只在池层乘一次（场景层输出最小卡数，池层 `planned_cards` 按 headroom + 8 卡对齐放大）；
- 三维约束取 max 不相加；
- 一次计算存完整快照，历史结果不受改库影响；
- 缺失是 null 不是 0，缺基线任务进 missing_items。

### 阶段 2：后端引擎移植与三池接线（工作量大头）

**2.1 新引擎 `engine/eval_engine.py`**（新文件，不动旧 `inference.py` 文件名下的历史代码——直接重写 `inference.py` 内容亦可，但保留模块名以减少 import 面改动；**推荐重写 inference.py**）：
- 忠实移植：`mem_constraint` / `prefill_constraint` / `decode_constraint` / `evaluate` / `aggregate`；
- 全部常数经 `params.reload()` 注入（新 params 结构）；芯片/模型/场景从 catalog 读；
- 入参 float（沿用 `to_engine()` 转换口径），卡数输出 int；
- 输出结构：`{cards, bottleneck(mem/prefill/decode), a/b/c 分解, tp/replicas, servers, warnings[], by_model 汇总}`。
- 删除旧引擎独有概念：混部抬升、SLA 回验加 DP、拓扑枚举、margin_factor 1.2（新口径 = 恰好满足 SLA 的最小卡数，余量由池层 headroom 表达）。

**2.2 `engine/business.py` 改造**：
- `estimate_scenario` → 调新引擎；场景层输出最小卡数 + bottleneck + 告警；
- `base_p` 新口径：`Σ 场景卡数 × chip.bf16_tflops ÷ 1000`（等效算力，BF16 基准）；`planned_cards` 沿用现有公式（headroom + 单机卡数对齐，**余量只在池层一次**）；
- `resolve_spec` 增加三组迁移映射（全部打 `MIGRATED_*` 告警，不静默）：
  - 场景别名：`long_gen→code、kb_qa→rag、deep_think→think、long_summary→gen_summary、ultra_long→long64k、custom→custom`；
  - 精度映射：`fp16→bf16、fp8/int8→w8a8、int4→w4a8`（`auto` 保留=按芯片默认 bf16）；
  - 芯片 key 映射：`"950(425T)"→950dt、"950(486T)"→950dt32、"950(547T)"→950dt36、"950(547T-96G)"→950dt36（无精确对应，额外打 CHIP_SUBSTITUTED 告警）`；
- `trace.variables` 输出新结构；**`derivations.describe_scenario` 同时支持新旧两种 trace 格式**（历史快照冻结不动）；
- `SCENE_BY_TEMPLATE` 旧模板映射按新场景 key 重写（qa/extract→rag、document→gen_summary、report→think）。

**2.3 `engine/calculator.py`（创新/研发池，公式不变、数据源换）**：
- lookup 源：`models()` → `inference_catalog.models() + store 自定义模型`（kind=inference-model 合并）；
- 字段推导适配层（创新/研发共用）：
  - `active_parameters_prefill/decode = active_b × 1e9`；`resident_parameters = total_b × 1e9`；
  - κ 结构修正沿用 arch（Dense 1.1 / MoE 1.2）；
  - KV cache 每序列字节从模型结构推导（与页面 `kvPerTokenGB` 同式）：MLA → `layers × (latent_dim + rope_dim) × kvBytes`；GQA/MHA → `2 × layers × kv_heads × kv_head_dim × kvBytes`；混合注意力 × `gqa_kv_fraction`；
  - 训练：`eligible_training_methods` 一律 `["lora","qlora"]`；`qlora_metadata_fraction` 取全局默认常量（实现时核对 models.json 现值定为默认，写入 schemas 默认值）；
- 删除：`multimodal`/vision proxy 分支、CV/unit 模型路径（旧 payload 中 yolo 等模型 lookup 失败 → `missing_items` 报 `MODEL_RETIRED`，不猜、不以 0 补齐）；
- 旧 model_id（`qwen3-8b` 等）→ 复用 `business.match_model_key` 归一化匹配新 key；对不上 → missing_items；
- 芯片折算 `_attach_cards` 不变（数据自动来自新 8 卡表；默认 `chip_key='910c'` 仍有效）。

**2.4 `schemas.py`**：
- `InferenceRequest.scene_key`：Literal 6 值 → **str**（catalog 校验；必须 str 才能兼容旧 payload 的旧 key 走迁移，Literal 收紧会让旧方案 PATCH 直接 422）；
- `weight_precision`：`Literal["auto","bf16","w8a8","w4a8","fp16","fp8","int8","int4"]`（旧值保留仅为兼容读，resolve 迁移；前端只展示新 4 项）；
- `kv_precision`：字段保留（兼容读）但引擎不再消费（页面口径 KV 字节由精度档决定）；
- `profile`：枚举值不变（optimistic/neutral/conservative），引擎内部映射 tier：optimistic→aggressive、neutral→standard、conservative→conservative；前端文案改「激进/均衡/保守」；
- `Allocation`：删除 `multimodal`、`images_per_request`（prune_payload 读路径自动剪旧字段，旧方案能打开）；
- `prefix_hit`：新引擎不消费 → 保留字段兼容读，resolve 忽略（或删除，二者取一，实现时随 prune 策略统一）。

**2.5 `main.py`**：
- `/inference/catalog`：出参含 chips 8（带 family 分组）、scenes 29（带 group/default_model_key）、models 32+custom、params 新 schema；
- `/inference/estimate`：切新引擎；
- `catalog_snapshot` 扩展：新计算存 `{inference_models, inference_chips, inference_scenes, params_effective}`（新口径可复现性）；旧快照结构不动；
- **`engine_version` → `engine-v2.0.0`**（health / 快照 / input_hash 全部跟随）；
- demo（L167-188）改用新目录 key 与新场景 key；
- **`启动.ps1` 两处 `engine_version -eq 'engine-v1.0.0'` 检查同步改为 v2.0.0**（漏改会导致启动脚本报「启动未成功」）；
- `imports.py` `suggest_task` 模型首选改新 key（qwen3_14b 等）；导入仍产 components 旧字段，走既有迁移链路。

## 5. 风险与守则

1. **口径变化必须对用户可见**：910C 系数 0.36→0.26、rag/think 默认并发 9→100/500、去掉 1.2 汇总余量（余量改由池层 headroom 表达，结果页同时展示「最小卡数」与「含余量卡数」），三因素叠加会使同一输入的总卡数明显变化——更新记录与页面说明需写清。
2. **input_hash 缓存坑**：验证参数影响走 `/inference/estimate`（不缓存），或让 payload 真变化。
3. **seed 只插不改**：chips/scenes/params 是文件 catalog（不走 store seed），直接改 json 即生效（重启）；但旧覆盖层在 store 里，需迁移逻辑。
4. **prune 与 strict 的分工**：删字段靠 prune_payload 读路径；枚举收敛必须保留旧值在 Literal 中，否则旧方案 PATCH 422。
5. **黄金值先行**：引擎移植的验收标准是与页面 JS 输出逐项一致，不允许「差不多」。
6. **推理评估页与后端双源**：本期页面保持自包含（数据同源自 2026-11 版）；后续可选让页面从 `/inference/catalog` 取数（列入 backlog，不在本期）。
