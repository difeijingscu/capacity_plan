## 2026-11-17：示例项目自动跟随当前引擎重算

- **现象**：示例项目的「企业知识问答」显示「三维最小 10 张 · 含余量对齐 8 卡后 16 张」，而 10 是偶数。16 是旧公式 `max(8, ceil(10 × 1.2 ÷ 8) × 8)` 的结果：先加 20% 余量（10 → 12），再按 8 卡/台向上对齐（12 卡 = 1.5 台 → 2 台 = 16 卡）。该 run 保存于 `engine-v2.1.0`，业务池当时还乘余量。
- **根因**：`POST /api/v1/demo` 的幂等分支直接返回已有示例方案（`reused: True`），从不检查示例的最新快照是不是当前引擎算的。于是每次引擎升级后，示例项目都停在首次生成的旧口径数字上——而示例正是给用户建立口径直觉的地方。
- **修法**：抽出 `calculation_snapshot(record, catalog, custom_models, custom_chips, params_snapshot, fingerprint)`（测算接口与示例自愈共用同一段落库逻辑）；`demo()` 复用已有示例时比较最新快照的 `engine_version`，不等则按当前引擎补一条新快照，历史快照保留。实测本地示例补出新 run：业务池 10 → 10 卡，总量 6.048 P。
- **验证**：`pytest -q` **1060 项通过**（新增 `test_demo_refreshes_a_stale_engine_snapshot`：首次 `demo` 不产生快照，第二次补一条当前口径快照，第三次不重复算）。

## 2026-11-17：业务场景池取消方案余量，规划卡数改为取偶（engine-v2.1.1）

- **背景**：业务池原有两步折算——`cards_planned = max(8, ceil(N × (1+h) / 8) × 8)`，`planned_p = base_p × (1+h)`。`h` 是方案级 `headroom`（`PlanInput.headroom`，缺省 0.20，`backend/app/schemas.py:202`）。同一份输入因此出现三个数：满足 SLA 的最小卡数 82、含余量并对齐整机的 104、含余量算力 55.104 P；而「约 13 台服务器」（104÷8）与池内 `servers=11`（逐场景 ceil 后求和）并存，用户无法判断哪个是结论。业务池的 SLA 约束（TTFT / TPOT）已经在 A/B/C 三维里算过，再乘 20% 属于重复保守。
- **改动（后端）**：`business.planned_cards(cards, unit)` 去掉 `headroom` 形参，改为 `max(unit, N + N % 2)`——只做奇数补偶，`unit=8` 保留为最小部署单元（1 卡需求仍规划 8 卡，避免出现 2 卡一台的不可交付配置）；`pool_summary` 去掉 `headroom` 形参，`planned_p = base_p`；`calculate` 的 `total_planned_p` 由 `Σbase_p × (1+h)` 改为 `Σ 各池 planned_p`（否则总量仍会替业务池加回余量）；业务场景 `scenario_summaries.planned_p` 同步改为 `base_p`。
- **改动（推导树与文案）**：`derivations.build_business_tree` 把「一次容量余量与部署粒度」节点替换为「规划卡数与部署粒度」（`N → 补偶后 cards_planned`，并写明不乘余量），`build_total_tree` 的业务池分支改「业务池不含容量余量」；`build_derivation` 的业务池不再输出「容量余量」输入与「增加一次容量余量」步骤，总量步骤由 `×(1+h)` 改为「Σ 各池建议容量」。
- **前端同步**：`BusinessPage` 场景行与 KPI 把「物理 / 含余量」改为「三维最小 / 规划卡数」；结果页表头改「建议算力（BF16）」「规划卡数（取偶）」，业务池卡片副标题按池区分；`CalculationDerivation`、`FxTree`、`PlanningBasis`、`PlanningOrganization`、`businessEvalContent` 的口径说明改为「业务池不含余量，创新/研发各含一次」。
- **历史快照不改写**：推导与文案按快照的 `engine_version` 分支——`engine-v2.1.1` 之前保存的 run 仍显示旧的「含余量卡数 = max(8, ceil(N×(1+h)÷8)×8)」与 `h=20%`，新 run 才走新口径。新增 `test_legacy_snapshot_keeps_headroom_wording` 锁定这条边界。
- **实测（test 项目基准方案）**：业务池 **104 卡 / 55.104 P → 82 卡 / 45.92 P**，`servers` 11 台，与页面「约 11 台服务器」自洽（原先 104÷8=13 台与 11 台并存的问题随之消失）；总量 **72.99 P**（业务 45.92 + 创新 27.01 + 研发 0.058）。示例方案业务池 16 卡 → **10 卡**（10 已偶数，无需补偶）。
- **未改**：创新/研发池仍按 `base_p × (1+h)` 放大一次并保留独立 1 卡冗余；`PlanInput.headroom` 字段与其缺省值保留（另两池仍在用），但业务页已无入口，两页「余量比例在方案设置中调整」的文案仍与实际不符，另批处理。

## 2026-11-17：空分配不再显示「替身模型」（P2-5）

- **问题**：创新池 `innovation.allocations`（或开发池 `development.models`）为**空列表**时，`PlanInput.coherent` 的份额校验会整块跳过（`if self.innovation.enabled and self.innovation.allocations`），payload 顺利通过；但三处说法互相矛盾——下拉框回显 `DeepSeek-V4-Flash`、「已选模型」；空态却写「选择模型后自动汇总」；缺项提示写「请填写支持人数与每人月 Token，并选择服务模型」，而这两个输入框里都有值。引擎侧 `calculate` 对 `not config.allocations` 记 `MISSING_WORKLOAD`，返回 `cards=null` / `BLOCKED`。界面上明明选着一个具体模型，引擎说没选。
- **更麻烦的是用户走不出来**：在下拉里再点一次已回显的 DeepSeek-V4-Flash —— `onChange` 不触发（值没变），一次 `edit` 都不会发生；改「每请求 Token」会写一条 `allocations`，但写的是 `edit` 里 `list.length ? [...] : [head]` 的兜底，仍然是补默认模型，用户并未选过；唯一出路是先关掉本池再打开（`setEnabled` 里有「数组为空就补一条默认分配」）。页面没有任何提示说明该这么做。
- **为什么仍要修**：正常 UI 操作产生不了这种数据（新建方案由 `default_innovation_allocations()` 带一条 `share=1`，各 `edit` 分支都写 `list.length ? ... : [head]`；存量 `data/planner.db` 两条方案多分配 0、多候选 0、份额异常 0）。它只从「直接调 API 写 payload / 手工改库 / 导入外部构造的 JSON」三个口子进来。但一旦进来，用户被卡死且无从自救，属防护性一致性问题。
- **修法（前端不显示假模型）**：两页都不再回落到默认模型。
  - `InnovationPage`：`modelKey = alloc?.model_id`（不再 `?? DEFAULT_MODEL`）；没有分配时下拉 `value` 为 `undefined`，显示 placeholder「选择提供创新服务的模型」；请求 Token 与输入占比**禁用**并提示「请求口径存在模型分配上，先选择服务模型」；空态改为「本方案没有服务模型记录，请先选择模型」；`setRequest` 无分配时直接 `message.warning` 拒绝，不再顺手建一条；`setEnabled` 只改开关。
  - `DevelopmentPage` 同一形态一并处理：`modelKey = entry?.model_id`、下拉留空、微调方法下拉 `disabled={!entry}`、空态「本方案没有候选模型记录，请先选择模型」、`setMethod` 无候选时拒绝、`setEnabled` 只改开关。
  - 选中任何一个模型都会触发 `onChange` 并写入一条（`share=1` / `method=lora`），原本卡死的状态变成一步可解。目录里找不到的旧 `model_id` 也给出明确说明「目录里没有「X」的结构数据，请重新选择」，不再笼统写「未选择模型」。
- **未采用的两条路**：不在 `coherent` 里补「启用时必须有分配」的硬校验——那会让这类 payload 连保存都 422、外部历史数据打开即不可保存；也不让引擎在空列表时回落默认模型——那等于引擎替用户填一个没填过的模型，快照里会记下虚构分配，比显示错误更难排查。引擎语义保持不变，仍按缺项处理。
- **测试**：两页各改写 2 项。`InnovationPage`：下拉留空（`selectedText` 为空、placeholder 可见、空态文案、两个输入 disabled）、开启本池不写模型而选择模型才写入（`mouseDown` 展开下拉、点 GLM-5.3 Flash、断言 `allocations` 一条 `share=1`）；`DevelopmentPage` 同构（方法下拉 disabled）。

## 2026-11-16：修「停止后重启报端口被占用」

- **症状**：`.\停止.ps1` 输出「原服务已退出，未停止其他进程。」，紧接着 `.\启动.ps1` 抛「端口8000已被其他程序占用，请使用启动.ps1 -Port 8008」。实测现场：8000 仍被本项目的 `python.exe -m uvicorn app.main:app --app-dir ...\backend`（pid 12164，父进程 4092 是 venv 转发壳）监听，`/api/v1/health` 正常返回 `engine-v2.0.4`，但 `data\server.json` 已被删除——旧的停止脚本在没能杀掉进程的情况下仍然无条件删掉状态文件，下一次启动就彻底失去追踪线索，只剩「端口被占用」。
- **根因**：①判定「是否本项目服务」用 `CommandLine.Contains($PSScriptRoot)`，字符串比较区分大小写、斜杠形式不归一，盘符或目录大小写变化即漏判；②结束进程只按状态文件里的 pid 逐个杀，`launcher_id`（venv 转发壳）被杀后真实解释器可能存活并继续占端口；③端口兜底清理只在 `-not $stopped` 时执行一次，且判定失败后不报告原因，随后删除状态文件。
- **改动（`停止.ps1`）**：以端口监听者为主依据——候选 pid 取「状态文件的 `process_id`/`launcher_id`/`pid`」+「记录端口与 8000 上的实际 listener」；进程判定归一化路径后比较，区分 `ours` / `other-sandbox`（另一个算力沙盘实例）/ `foreign`（其他程序）/ `gone`；命中 `ours` 时按 `ParentProcessId` 递归取整棵进程树后逆序强杀（覆盖壳 → 真实解释器 → 子进程）；杀完轮询端口释放最多 3 秒，仍有残留则输出 pid 与「可手动结束」命令、**保留** `server.json` 并 `exit 1`；确认释放后才删状态文件。`other-sandbox` 只提示不自动结束，避免误杀另一个目录的实例。
- **改动（`启动.ps1`）**：端口上的进程判定为 `ours` 且 `/api/v1/health` 返回 `ok` 时接管现有服务并写回状态文件（状态文件丢失、pid 失效不再误报「被其他程序占用」）；判定为 `other-sandbox` 时提示对方 pid 与命令行；`foreign` 时提示 pid 与进程名；立即启动失败不再依赖 `health` 单独判定（新增进程树清理后再探测端口）。兼容旧版只写 `pid` 的状态文件。
- **验证**（7 个场景，均在本机实测）：正常启动 → 停止 → 端口释放；无服务时停止输出「没有正在运行的本项目服务。」；`server.json` 删除但服务在跑 → 停止按端口杀掉（pid 22876）；状态文件写死失效 pid（999999）但端口有服务 → 仍按端口杀掉（pid 5948）；端口被无关进程（powershell 的 TcpListener）占用 → 报「已被其他程序占用（pid 25560，进程 powershell）」且不误杀；停止两次幂等；连续 stop/start 各两轮 health 均为 `ok`。两脚本保持 UTF-8 with BOM（PowerShell 5.1 中文识别必需）并通过语法解析校验。

## 2026-11-09：算力命名口径拆分为「单位」与「精度基准」（v1.3.2）

原先的 `P16` / `T16` 把两件事压在一个后缀里：`P` / `T` 是**量级单位**（10¹⁵ / 10¹² FLOPS），`16` 是**精度基准**（BF16 稠密）。混写会让人读成「16 位精度下的 P」，也无法表达 FP8 基准。现在拆开：

| 表达对象 | 旧写法 | 新写法 |
|---|---|---|
| 只是算力数值 | `5.00 P16` / `163 T16` | `5.00 P` / `163 T` |
| 说明该处是 BF16 等效 | `P16 等效` | `BF16 基准`（另可写 FP16 / FP8） |

改动范围：

- 前端 `api.ts` 的 `capacity()` 不再拼 `16` 后缀，`0` 显示 `0 T`；`api.test.ts` 断言同步。
- 业务场景页列内标注「BF16 等效」，结果页列标题写「需求算力（BF16）」「建议算力（BF16，含余量）」；规划依据「P16 / T16」条目改为「算力单位 P / T」。
- 后端推导步骤单位由 `P16` 改为 `P`，公式写作 `P = 卡数 × 单卡 BF16 算力(T) ÷ 1000`；`trace.units`、`calculator` 注释与 `business` 文件头口径说明同步。
- 文档（README、开发笔记、设计文档、测试报告、对比报告、部署指南）统一为「单位 P / T + 精度基准 BF16」；历史条目保留原写法并标注。
