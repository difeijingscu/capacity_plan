## 1. 架构与数据流

```
浏览器（React 19 + antd 5 + echarts，构建产物在 frontend/dist）
        │  fetch /api/v1/*
        ▼
FastAPI 单进程（backend/app/main.py）
   ├─ app.store.Store       → SQLite data/planner.db（单表 records，kind + JSON body）
   ├─ app.engine.calculator → 纯函数计算引擎（不联网、不读写盘、不读时钟、不 import AI）
   ├─ app.derivations       → 从「计算快照」反推可读推导（只读快照，不读当前表单/模型库）
   ├─ app.imports           → xlsx / 文本导入、列映射、单位识别
   └─ app.assistant         → 可选 AI 接口（页面已不使用，仅后端保留）
        │  StaticFiles 挂载 dist/assets + SPA fallback
        ▼
127.0.0.1:8000
```

关键设计约束（改动时必须守住）：

1. **引擎是纯函数**：`calculate(plan, models, sensitivity)` 输入 `PlanInput` + 模型目录快照，输出 JSON 报告。任何全局状态、随机、当前时间都不允许进入。
2. **计算即快照**：一次计算把 `input_snapshot`（当次 payload）、`catalog_snapshot`（当次模型目录）、`engine_version`、`input_hash` 一起存进 `calculation` 记录。之后改模型库/改表单都不影响历史结果。
3. **Decimal 全链路**：所有数值用 `Decimal`，`clean()` 在出口把 Decimal 转字符串。前端只负责展示，不做精度换算。
4. **异步任务**：`ThreadPoolExecutor(max_workers=2)` 执行 `calculation` 与 `assistant` 两类 job；进程重启时 `Store.recover()` 把残留 `RUNNING/QUEUED` 置为 `INTERRUPTED`。

## 2. 计算口径与代码对照

### 2.1 业务池（`calculator.compute_task` + `inference` + `memory_for`）

| 步骤 | 公式 | 代码位置 |
|---|---|---|
| 在线人数→请求速率 | λ = U × r × calls_per_request ÷ 60 | `calculator.py:123-126` |
| 输入长度（图文） | Li = input_tokens + (图片数 + 抽帧数) × 每图视觉Token | `:146-147` |
| 生成长度 | Lg = answer_tokens + reasoning_tokens | `:127` |
| 每请求工作量 | Fp = 2·Np·Li·κp；Fd = 2·Nd·Lg·κd | `inference()` `:71-81` |
| 结构修正 κ | Dense 1.1 / MoE 1.2（可被 `kappa_prefill/decode` 覆盖） | `:155-156` |
| 基础容量 | C = λ·((Fp + Fvision)/ηp + Fd/ηd) ÷ 10¹⁵ | `inference()` `:76` |
| 有效需求（不含效率） | E = λ·(Fp + Fvision + Fd) ÷ 10¹⁵ | `:77` |

默认效率：ηp = 0.35，ηd = 0.15（`schemas.py:37-38`）。视觉代理：Fvision = Fp × 0.20，每图 1024 视觉 Token（`schemas.py:45-47`），触发时打 `VISION_PROXY` 警告。

**显存**（`memory_for` `:84-116`，仅算「未含余量」的分项，余量在组汇总时加一次）：

```
weight  = resident × weight_bits/8 ÷ 1e9 × (1 + 量化元数据比例) × replicas
runtime = max(2, weight/replicas × 0.1) × replicas
W_target = ttft_seconds + Lg / output_tokens_per_second
C_expected = λ × W_target         → sequences = max(1, ceil(C_expected))（λ=0 且未预热时为 0）
bpt      = 2 × layers × kv_heads × head_dim × kv_bytes
cache    = sequences × (Li + Lg) × bpt ÷ 1e9
memory_gb = (weight + cache + runtime) ÷ (1 − 0.15)      ← summarize_memory :229
```

组内规则（`summarize_memory`）：同组 `weight_gb`、`runtime_gb` 取 **max**（共享权重），`cache_gb` **求和**；组键 = `model_id | serving_profile | weight_bits | kv_bytes | deployment_group | (独立部署时 task.id)`（`:121`）。

### 2.2 创新服务池（`:286-309`）

```
Q_month = users × growth × quota_per_user_month × usage_ratio
T       = service_days × service_hours_per_day × 3600
λ_model = Q_month × share ÷ T × peak_factor ÷ request_total_tokens
Li = request_total_tokens × input_fraction；Lg = request_total_tokens × (1 − input_fraction)
→ 进入同一 llm-phases 公式，各模型份额互斥、峰值同时发生
```

默认：22 日 × 8 小时、peak_factor 3、额度使用率 100%、输入占比 80%、单请求 2560 Token（`schemas.py:98-118`）。
图文额度特殊处理：`allocation.multimodal=true` 时把 `visual_tokens_per_image` 置 0，避免视觉 Token 二次计入（`:302-303`）。

### 2.3 开发测试池（`:311-365`）

```
F_train = k_train × N_active_train × D × E
C_train = F_train ÷ (H × 3600 × ηtrain × 10¹⁵)          # k=4, ηtrain=0.25

M_base    = resident × (0.5 若 qlora 否则 2) ÷ 1e9 (× (1+qlora元数据))
M_adapter = resident × adapter_fraction(0.005) × 16 ÷ 1e9
M_act     = max(8, 0.2×M_base) × (sequence_length/2048) × micro_batch
M_work    = max(2, 0.1×M_base)
M_job     = (M_base + M_adapter + M_act + M_work) ÷ 0.85

聚合：C_train_pool = train_slots × max(各模型 C_train)；C_eval 同理
      并行档位 = train + eval；串行档位（light）= max(train, eval)
```

强度档位常量在 `calculator.py:23-27`（`INTENSITIES`），与 `schemas.py` 的字段默认值**是两处独立定义**，改动需同步（有测试守着，见 9.1）。

### 2.4 汇总与余量（`pool_summary` `:235-241`、`calculate` `:367-372`）

```
每池 planned_p = base_p × (1 + headroom)      headroom 默认 0.20
总建议容量     = Σ三池 planned_p（各池已含余量，汇总不再乘一次）
增长系数       = (1+annual_growth)^(年限/365.25)，仅当 input_time_basis = current_growth
```

增长只作用于规模字段（`online_users / request_rate / streams / images_per_second / units_per_second / total_units`）与创新池人数，不改容量本身（`:270-274`、`:293`）。

### 2.5 费用附录（`cost_estimate` `:396-427`）

```
n_compute = ceil(planned_p / card.dense_p16)
n_memory  = ceil(memory_gb / card.memory_gb)   （显存状态不是 COMPLETE/PROXY 时置 null）
n_ref     = max(n_compute, n_memory)           ← 每个池各自取整后再相加
金额区间   = Σ n_ref × 单卡报价下限 / 上限
```

调整参考卡规格**不影响** `planned_p`，只改卡数。

## 3. 状态语义：四个互相独立的状态位

| 状态 | 取值 | 含义 | 位置 |
|---|---|---|---|
| `completeness` | COMPLETE / PARTIAL / BLOCKED / DISABLED | 该池是否所有启用任务都已计入 | `:239` `:371` |
| `evidence_grade` | 恒为 C | 经验估算，无实测校准 | `:122` `:241` |
| `memory.status` | COMPLETE / PROXY / WEIGHT_LOWER_BOUND / UNKNOWN | 显存能否给出完整值 | `:105-116` `:224-231` |
| `latency_status` | 恒为 UNVERIFIED | 响应时间目标未经实测 | `:122` |

硬性约定：**缺失是 `null`，不是 `0`**。缺基线的任务进 `missing_items` 并在页面列明原因，不参与求和。已禁用的池是明确的 0（DISABLED）。原生精度任务若无 `reference_mapping`，`base_p=null` 且给 `PRECISION_NOT_COMPARABLE`，不会被自动换算。

## 5. 存储结构

单表设计，`Store` 只做 CRUD，不做业务校验：

```sql
records(id TEXT PK, kind TEXT, body TEXT/*JSON*/, revision INT, created_at TEXT, updated_at TEXT)
```

`kind` 取值：`project / plan / plan_history / calculation / job / import / model / card / baseline / price / cost / message / proposal / settings`。
迁移文件只有 `backend/migrations/versions/0001_records.py`（建这张表），实际建表也由 `Store.__init__` 的 `meta.create_all` 兜底。SQLite 开启 WAL + 外键。

## 6. 前端结构

单页应用，7 个页面全部写在 `App.tsx` 的局部函数里（`projectsPage / businessPage / innovationPage / developmentPage / resultsPage / settingsPage` + 两个静态说明页组件）：

- 状态源：`payload`（完整 `PlanInput` JSON）+ `dirty` 标记；所有编辑走 `edit(mutator)` 做 `structuredClone` 后再改，避免就地修改。
- 保存：`PATCH /plans/{id}` 带 `expected_revision`，成功后清 `dirty`。
- 预估算力：业务场景页 650ms 防抖调 `POST /preview-calculation`，只在列表里显示每场景的 `planned_p`。
- 结果页 4 张指标卡可点击展开 `CalculationDerivation`（抽屉），显示逐步代入；「查看计算依据」抽屉直接展示单任务 `trace` JSON。
- 数值展示统一走 `api.ts` 的 `capacity()`（≥1 显示 P16，否则 T16，3 位有效数字）与 `num()`。

## 9. 风险与坑（按踩中概率排序）

**9.1 默认值双源**
`schemas.py` 的字段默认值 与 `calculator.py` 的 `TEMPLATES` / `INTENSITIES` 是两份独立定义。改一处不改另一处会导致「页面显示值 ≠ 计算采用值」。已有 `test_display_defaults_match_calculation_defaults` 守着，但只覆盖已被测试引用的字段。

**9.2 seed 只插不改**
`Store.publish_seeds()` 仅在 `id` 不存在时插入（`store.py:75-78`）。所以**直接改 `catalogs/models.json` 对已有 `data/planner.db` 无效**。生效方式三选一：删库重建（会丢项目数据）、新建 revision（`POST /catalog/model-revisions` + publish）、或改 id。

**9.3 存量快照不跟随模型库**
历史 `calculation` 用的是 `catalog_snapshot`。发布新模型版本后，旧结果不会变，这是刻意设计（`test_model_publish_does_not_rewrite_history`）。排查「为什么结果没变」时先看这条。

**9.4 混合缓存是保守代理**
Qwen3.6 系列 `cache.type=hybrid`：代码按全部 `layers` 算 GQA 缓存，再给每个线性层加 4 MiB/序列状态（`:108-114`），状态标 `PROXY`。数值偏大，不要当精确值对外引用。

**9.5 QLoRA 必须有元数据**
`weight_bits<16` 或 `qlora` 且模型缺 `quantization_metadata_fraction` / `qlora_metadata_fraction` 时直接抛 `UNSUPPORTED_PROFILE` / `MISSING_BASELINE`，不会静默降级。

**9.6 长上下文与特殊架构门槛**
`max(Li,Lg)>32768` 或 `cache.type=unknown` 的 MoE，必须显式 `allow_proxy=true`，否则报 `MISSING_BASELINE`（`:151-154`）。这是产品有意的「不给没依据的数」。

**9.7 健康检查路径**
是 `/api/v1/health`，不是 `/api/health`（后者 404，容易误判服务挂了）。

**9.8 热点文件**
`main.py`（41 路由 + 全部业务校验）与 `App.tsx`（245 行、单行超长）是唯一入口，多人并行改动极易冲突。若要做较大改造，建议先把 `main.py` 按资源域拆 router（plans / catalog / costs / assistant），`App.tsx` 按页面拆组件——拆完跑一遍 58 个测试即可确认无回归。

**9.9 计算并发**
只有 2 个线程的池，长任务（1000 场景 ≈ 毫秒级，实际压力不大）与 AI 助手任务共用；重启会把未完成任务置 `INTERRUPTED`，前端 `waitJob` 会轮询 300 次 × 300ms 后超时。

## 10. 产品边界（不是 bug）

- 无账号体系、无审批流，仅本机单用户。
- 无文档导出（PDF/Word/Excel 输出均未实现）。
- 费用仅含加速卡购置，不含整机、网络、存储、软件、运维。
- 价格库初始为空，需人工录入来源、日期与区间；过期报价只提示不删除。
- 全部效率（η）、结构修正（κ）、训练系数（k）、视觉代理比例均为 C 级经验假设，`latency_status` 恒为 UNVERIFIED。
- AI 助手页面已移除，`assistant.py` 与相关接口仅为保留扩展，不参与日常规划。
