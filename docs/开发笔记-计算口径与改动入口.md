## 1. 架构与数据流

```
浏览器（React 19 + antd 5 + echarts，构建产物在 frontend/dist）
        │  fetch /api/v1/*
        ▼
FastAPI 单进程（backend/app/main.py）
   ├─ app.store.Store       → SQLite data/planner.db（单表 records，kind + JSON body）
   ├─ app.engine.calculator → 纯函数计算引擎（不联网、不读写盘、不读时钟、不 import AI）
   ├─ app.engine.inference  → 推理算力评估引擎（A/B/C 四约束，纯函数，见第 11 节）
   ├─ app.derivations       → 从「计算快照」反推可读推导（只读快照，不读当前表单/模型库）
   ├─ app.imports           → xlsx / 文本导入、列映射、单位识别
   └─ app.assistant         → 可选 AI 接口（页面已不使用，仅后端保留）
        │  StaticFiles 挂载 dist/assets + SPA fallback
        ▼
127.0.0.1:8000
```

关键设计约束（改动时必须守住）：

1. **引擎是纯函数**：`calculate(plan, models, sensitivity)` 输入 `PlanInput` + 模型目录快照，输出 JSON 报告。任何全局状态、随机、当前时间都不允许进入。
2. **计算即快照**：一次计算把 `input_snapshot`（当次 payload）、`catalog_snapshot`（当次模型目录）、`engine_version`、`input_hash` 一起存进 `calculation` 记录。之后改模型库/改表单都不影响历史结果。
3. **Decimal 全链路**：所有数值用 `Decimal`，`clean()` 在出口把 Decimal 转字符串。前端只负责展示，不做精度换算。
4. **异步任务**：`ThreadPoolExecutor(max_workers=2)` 执行 `calculation` 与 `assistant` 两类 job；进程重启时 `Store.recover()` 把残留 `RUNNING/QUEUED` 置为 `INTERRUPTED`。

## 2. 计算口径与代码对照

### 2.1 业务池（v2.0.0 起：逐场景调用页面引擎，`engine/business.py` + `engine/inference.py`）

业务池不再按「请求速率 × 分阶段 FLOP」自算，而是把每个场景翻成推理引擎的入参，直接取引擎的
卡数与需求算力。**v2.0.0 起引擎就是推理评估页的同一套公式（页面引擎忠实移植）**，业务池与
推理评估页共用一条链路；旧 llm-phases 公式仅剩创新池在用，见 2.1.2。

| 步骤 | 内容 | 代码位置 |
|---|---|---|
| 场景 → 引擎入参 | `Scenario.inference` → `to_engine()`；缺配置时按旧字段迁移 | `business.resolve_spec` |
| 三维约束 | max(显存 A, Prefill B, Decode C) → 奇数补偶；TTFT/TPOT 回验出告警 | `inference.estimate` |
| 等效算力 | `base_p = cards × chip.bf16_tflops ÷ 1000`（BF16 等效参考） | `business.estimate_scenario` |
| 含余量卡数 | `max(cards+unit, ceil(cards×(1+h)/unit)×unit)`，h = `plan.headroom`，unit = 8 | `business.planned_cards` |
| 池汇总 | `base_p = Σ各场景 base_p`；`planned_p = base_p × (1+h)`；卡数按物理台数相加 | `business.pool_summary` |

三条口径铁律（改代码前务必确认）：

1. **卡数与算力（P）不同量纲**。`cards` 是物理卡数（8 张 = 1 台），`base_p` 是卡数折算的等效参考算力，不能直接相加或相比。
2. **余量只在池层乘一次**。场景层 `cards` 是最小卡数（不含余量）；含余量卡数按单实例对齐放大后池层直接相加，不再重复乘。
3. **三维取 max，不相加**。同一批卡同时承担 Prefill 与 Decode；卡数取奇数会补偶。

迁移规则（`business.resolve_spec`，前端 `BusinessPage.legacyState` 同口径）：`components` 存在但没有 `inference` 时按「模型名归一化匹配（`match_model_key`）+ 任务模板（qa/extract→rag、document→gen_summary、report→think）」推导，打 `MIGRATED_INFERENCE` / `MIGRATED_MODEL`；连模型字段都没有则报 `MISSING_MODEL`；模型名对不上 v2 清单、或任务类型为 `cv/unit/native` 时报 `MODEL_RETIRED`（都不落默认模型硬算，计入未计入项）。旧方案里的场景档（kb_qa 等）、精度（fp16/fp8/int8/int4/auto）与芯片 key（如「950(425T)」）在 `_migrate_spec` 里映射到 v2 目录并打 `MIGRATED_SCENE` / `MIGRATED_PRECISION` / `CHIP_MIGRATED`，不静默。前端状态列据此显示「旧字段推导 / 待补模型 / 不支持」。

**历史字段兼容**：`schemas.prune_payload` 在**读路径**按当前 schema 递归剪掉已下线字段（`GET /plans/{id}`、`GET /projects`、撤销、测算），写入仍走 `extra="forbid"` 严格校验——这样旧方案能打开，而写错字段名不会被静默吞掉。

### 2.1.2 仍被创新池复用的 llm-phases 口径（`calculator.py`）

v2.0.0 起 CV / 图文路径已删除（`vlm` 同 text，`cv/unit/native` 报 `MODEL_RETIRED`）；模型查询
优先直查，再经 `match_model_key` 归一化到 32 条 LLM 清单或自定义模型（`inference_model_view`
把 `total_b/active_b` 适配成显存推导需要的结构字段）。

| 步骤 | 公式 | 代码位置 |
|---|---|---|
| 在线人数→请求速率 | λ = U × r × calls_per_request ÷ 60 | `calculator.py` |
| 生成长度 | Lg = answer_tokens + reasoning_tokens | 同上 |
| 每请求工作量 | Fp = 2·Np·Li·κp；Fd = 2·Nd·Lg·κd | `inference()` |
| 结构修正 κ | Dense 1.1 / MoE 1.2（可被 `kappa_prefill/decode` 覆盖） | 同上 |
| 基础容量 | C = λ·(Fp/ηp + Fd/ηd) ÷ 10¹⁵ | `inference()` |
| 有效需求（不含效率） | E = λ·(Fp + Fd) ÷ 10¹⁵ | 同上 |

**显存**（`memory_for` `:84-116`，仅算「未含余量」的分项，余量在组汇总时加一次）：

```
weight  = resident × weight_bits/8 ÷ 1e9 × (1 + 量化元数据比例) × replicas
runtime = max(2, weight/replicas × 0.1) × replicas
W_target = ttft_seconds + Lg / output_tokens_per_second
C_expected = λ × W_target         → sequences = max(1, ceil(C_expected))（λ=0 且未预热时为 0）
bpt      = 2 × layers × kv_heads × head_dim × kv_bytes
cache    = sequences × (Li + Lg) × bpt ÷ 1e9
memory_gb = (weight + cache + runtime) ÷ (1 − 0.15)      ← summarize_memory :229
```

组内规则（`summarize_memory`）：同组 `weight_gb`、`runtime_gb` 取 **max**（共享权重），`cache_gb` **求和**；组键 = `model_id | serving_profile | weight_bits | kv_bytes | deployment_group | (独立部署时 task.id)`（`:121`）。

### 2.2 创新服务池（`:286-309`）

```
Q_month = users × quota_per_user_month × usage_ratio
T       = service_days × service_hours_per_day × 3600
λ_model = Q_month × share ÷ T × peak_factor ÷ request_total_tokens
Li = request_total_tokens × input_fraction；Lg = request_total_tokens × (1 − input_fraction)
→ 进入同一 llm-phases 公式，各模型份额互斥、峰值同时发生
```

默认：22 日 × 8 小时、peak_factor 3、额度使用率 100%、输入占比 80%、单请求 2560 Token（`schemas.py:98-118`）。
图文额度特殊处理：`allocation.multimodal=true` 时把 `visual_tokens_per_image` 置 0，避免视觉 Token 二次计入（`:302-303`）。

**卡数（v1.4 新增，`calculator.cards_for_pool` `:211-260`）**：创新池主链路现在直接输出卡数，不再只在费用附录里出现。

```
n_compute = ⌈planned_p × 1000 ÷ chip.bf16_tflops⌉        算力卡数
n_memory  = ⌈memory_gb ÷ chip.memory_gb⌉                显存卡数
n_card    = max(n_compute, n_memory)                    与业务池同口径取大
cards_planned = max(n_card + 1, ⌈planned_p×(1+h)÷chip⌉)  按余量放大且至少多一张
servers   = ⌈n_card ÷ 8⌉                                整机台数
capacity_p = n_card × chip.bf16_tflops ÷ 1000           等效算力（P，BF16 基准）（与业务池同量纲）
```

- 芯片来自 `Innovation.chip_key`（默认 `910c`），规格取 `catalogs/inference_chips.json`，与业务池共用同一套，两池卡数才可比。
- **池层不对齐整机**。业务池的 `planned_cards` 按单实例卡数对齐，是因为它必须给出可部署拓扑；池层混机型，按 8 卡对齐会把「1 卡」放大成「9 卡」，属于口径错误。
- `chip_key` 为空或芯片不存在时 `cards=null` 并在 `cards_detail.reason` 写明原因，**不按默认芯片硬算**。
- 推导过程全在 `cards_detail`（compute_cards / memory_cards / bottleneck / 芯片规格），供抽屉与审计；`bottleneck` 只有「算力 / 显存 / 持平」三种。
- 开发测试池同口径（`Development.chip_key`），聚合方式是「槽位数 × 最大单任务」。

### 2.4 汇总与余量（`pool_summary`、`calculate`）

```
每池 planned_p = base_p × (1 + headroom)      headroom 默认 0.20
总建议容量     = Σ三池 planned_p（各池已含余量，汇总不再乘一次）
```

v1.1 起**没有增长系数**：`planning_start / planning_end / input_time_basis / annual_growth` 与报告里的 `growth_factor` 全部删除，规模字段原样进入公式，不做任何时间外推。需要考察增长时由用户直接改大在线人数/额度后重算，或复制方案做对比。

### 2.5 费用附录（`cost_estimate` `:396-427`）

```
n_compute = ceil(planned_p / card.dense_p16)
n_memory  = ceil(memory_gb / card.memory_gb)   （显存状态不是 COMPLETE/PROXY 时置 null）
n_ref     = max(n_compute, n_memory)           ← 每个池各自取整后再相加
金额区间   = Σ n_ref × 单卡报价下限 / 上限
```

调整参考卡规格**不影响** `planned_p`，只改卡数。

**与 v1.4 池卡数的关系**：费用附录是独立口径——它用 `catalog/cards` 的参考卡（NV 系 `dense_p16` 为 PFLOPS），目的是给出「同算力大约等于几张参考卡」的横向量，**不替代池内卡数**。`pools[].cards` 回答「按所选昇腾芯片要几张卡」，`cost_estimate` 回答「换成参考卡大约几张、要多少钱」。两者都保留，但引用时须说明用的是哪一个。

## 3. 状态语义：四个互相独立的状态位

| 状态 | 取值 | 含义 | 位置 |
|---|---|---|---|
| `completeness` | COMPLETE / PARTIAL / BLOCKED / DISABLED | 该池是否所有启用任务都已计入 | `:239` `:371` |
| `evidence_grade` | 恒为 C | 经验估算，无实测校准 | `:122` `:241` |
| `memory.status` | COMPLETE / PROXY / WEIGHT_LOWER_BOUND / UNKNOWN | 显存能否给出完整值 | `:105-116` `:224-231` |
| `latency_status` | 恒为 UNVERIFIED | 响应时间目标未经实测 | `:122` |

硬性约定：**缺失是 `null`，不是 `0`**。缺基线的任务进 `missing_items` 并在页面列明原因，不参与求和。已禁用的池是明确的 0（DISABLED）。原生精度任务若无 `reference_mapping`，`base_p=null` 且给 `PRECISION_NOT_COMPARABLE`，不会被自动换算。

## 5. 存储结构

单表设计，`Store` 只做 CRUD，不做业务校验：

```sql
records(id TEXT PK, kind TEXT, body TEXT/*JSON*/, revision INT, created_at TEXT, updated_at TEXT)
```

`kind` 取值：`project / plan / plan_history / calculation / job / import / model / card / baseline / price / cost / message / proposal / settings / inference-model / inference-params`。
其中 `inference-params` 只有一条 `id=active` 的记录，存参数的**覆盖层**（不是默认值），默认值仍在 `catalogs/inference_params.json`。
迁移文件只有 `backend/migrations/versions/0001_records.py`（建这张表），实际建表也由 `Store.__init__` 的 `meta.create_all` 兜底。SQLite 开启 WAL + 外键。

## 6. 前端结构

单页应用。项目概览、创新、研发、结果、设置写在 `App.tsx` 的局部函数里；业务场景与推理参数已拆成独立组件（`BusinessPage.tsx` / `InferenceParamsPage.tsx`），推理评估在 `InferencePage.tsx`，自定义模型登记弹窗由 `CustomModelModal.tsx` 共用：

- 状态源：`payload`（完整 `PlanInput` JSON）+ `dirty` 标记；所有编辑走 `edit(mutator)` 做 `structuredClone` 后再改，避免就地修改。
- 保存：`PATCH /plans/{id}` 带 `expected_revision`，成功后清 `dirty`。
- 预估算力：业务场景页 650ms 防抖调 `POST /preview-calculation`，列表里显示每场景的 `base_p`（需求算力）与 `cards_planned`（含余量卡数）；注意 `calculate` 有 input_hash 缓存，同一 payload 改了参数再算会命中旧快照，验证参数影响要走一次真实的 payload 变更或直接调 `/inference/estimate`。
- 业务场景的推理配置以 `specOf()` 展示：有 `inference` 就直接用；只有旧字段时用与后端 `business._norm` 相同的归一化规则匹配等价模型，保证「表里显示的模型」就是「实际参与计算的模型」。改动一律走 `write()`，缺模型时先提示选模型，不落默认值。
- 结果页 4 张指标卡可点击展开 `CalculationDerivation`（抽屉），显示逐步代入；「查看计算依据」抽屉直接展示单任务 `trace` JSON。
- 数值展示统一走 `api.ts` 的 `capacity()`（≥1 显示 P，否则 T，3 位有效数字；不带精度后缀）与 `num()`。

## 7. 实测复核：接口值 vs 手算值

用运行中的服务跑一个最小业务场景（v1.3：Qwen3-8B、昇腾910C、知识库问答档、100 路并发、中性档）：

```json
POST /api/v1/inference/estimate
{"model_key":"qwen3_8b","chip_key":"910c","scene_key":"kb_qa","concurrency":100}

POST /api/v1/preview-calculation
{"payload":{"scenarios":[{"id":"s1","name":"知识问答","inference":{
  "model_key":"qwen3_8b","chip_key":"910c","scene_key":"kb_qa","concurrency":100}}]}}
```

下面这张表是**旧 llm-phases 口径**的手算复核（现在只对创新池成立，8B 合成模型、100 人、qa 模板）：
```

| 量 | 接口输出 | 按公式手算 | 是否一致 |
|---|---|---|---|
| λ | 0.833333… | 100×0.5×1÷60 | ✓ |
| Fp | — | 2×8.19073536e9×2048×1.1 = 3.6904177e13 | ✓（由 base_p 反推） |
| Fd | — | 2×8.19073536e9×512×1.1 = 9.2260443e12 | ✓ |
| base_p | 0.1391228903814095238095238095 | 0.1391228903814095238095238095 | ✓ 逐位一致 |
| planned_p | 0.1669474684576914285714285714 | base×1.2 | ✓ |
| weight_gb | 16.381470720 | 8.19073536e9×16/8/1e9 | ✓ |

## 9. 风险与坑（按踩中概率排序）

**9.1 默认值双源**
`schemas.py` 的字段默认值 与 `calculator.py` 的 `TEMPLATES` / `INTENSITIES` 是两份独立定义。改一处不改另一处会导致「页面显示值 ≠ 计算采用值」。已有 `test_display_defaults_match_calculation_defaults` 守着，但只覆盖已被测试引用的字段。

**9.2 seed 只插不改**
`Store.publish_seeds()` 仅在 `id` 不存在时插入（`store.py:75-78`）。所以**直接改 `catalogs/models.json` 对已有 `data/planner.db` 无效**。生效方式三选一：删库重建（会丢项目数据）、新建 revision（`POST /catalog/model-revisions` + publish）、或改 id。

**9.3 存量快照不跟随模型库**
历史 `calculation` 用的是 `catalog_snapshot`。发布新模型版本后，旧结果不会变，这是刻意设计（`test_model_publish_does_not_rewrite_history`）。排查「为什么结果没变」时先看这条。

**9.4 混合缓存是保守代理**
Qwen3.6 系列 `cache.type=hybrid`：代码按全部 `layers` 算 GQA 缓存，再给每个线性层加 4 MiB/序列状态（`:108-114`），状态标 `PROXY`。数值偏大，不要当精确值对外引用。

**9.5 QLoRA 必须有元数据**
`weight_bits<16` 或 `qlora` 且模型缺 `quantization_metadata_fraction` / `qlora_metadata_fraction` 时直接抛 `UNSUPPORTED_PROFILE` / `MISSING_BASELINE`，不会静默降级。

**9.6 长上下文与特殊架构门槛**
`max(Li,Lg)>32768` 或 `cache.type=unknown` 的 MoE，必须显式 `allow_proxy=true`，否则报 `MISSING_BASELINE`（`:151-154`）。这是产品有意的「不给没依据的数」。

**9.7 健康检查路径**
是 `/api/v1/health`，不是 `/api/health`（后者 404，容易误判服务挂了）。

**9.8 热点文件**
`main.py`（41 路由 + 全部业务校验）与 `App.tsx`（245 行、单行超长）是唯一入口，多人并行改动极易冲突。若要做较大改造，建议先把 `main.py` 按资源域拆 router（plans / catalog / costs / assistant），`App.tsx` 按页面拆组件——拆完跑一遍 56 个测试即可确认无回归。

**9.9 计算并发**
只有 2 个线程的池，长任务（1000 场景 ≈ 毫秒级，实际压力不大）与 AI 助手任务共用；重启会把未完成任务置 `INTERRUPTED`，前端 `waitJob` 会轮询 300 次 × 300ms 后超时。

**9.10 旧方案字段不兼容（v1.1 引入）**
`StrictModel` 是 `extra="forbid"`，所以带 `planning_start / planning_end / input_time_basis / annual_growth`，或开发池带 `eval_*`、`train_eval_parallel`、`DevModel.eval_task_type` 的旧 payload，现在会直接 **422 INVALID_INPUT**。数据库里已存的历史方案不会自动清洗：`GET /plans/{id}` 能读出来，但只要原样 PATCH 或计算就会失败。需要迁移脚本时，按字段白名单剔除后再保存。

## 11. 推理算力评估引擎（v1.2 新增；v2.0.0 起为唯一推理口径）

**v2.0.0 里程碑**：`engine/inference.py` 整体重写为「推理评估页面引擎的忠实移植」——页面
`inference-eval.html` script#2 里的 mem_constraint / prefill_constraint / decode_constraint /
evaluate / aggregate 纯函数逐一对应 Python 实现，以 938 例黄金值 + aggregate 锚点验收
（A 维精确一致；B/C 卡数一致、时延 1e-9 相对误差）。业务池（2.1 节）、推理评估页、
`/api/v1/inference/*` 从此共用同一套公式与参数；旧「混部抬升 + SLA 回验加 DP」v1 引擎已删除。

### 11.1 链路与代码位置

```
输入：模型结构 + 芯片规格 + 场景档位 + 精度档（bf16/w8a8/w4a8）+ 并发与时延目标
   ↓
① 显存 A     权重（按精度字节）+ KV 缓存（MLA/GQA/混合逐层计数）→ 权重装载宽度 × 副本
② Prefill B  max(吞吐下限 N1, M/G/1 排队时延下限 N2)
③ Decode C   枚举 分片宽度 × 副本数，取满足 TPOT 的最小卡数（带宽受限/算力地板出告警）
   ↓ 卡数 = max(A, B, C)，奇数补偶（最小卡数，余量在池层）
④ 时延预测：TTFT 预测 vs 目标、Decode 步长 vs TPOT，打 longInput/longOutput/crossNode/
   bandLimited/tpotShort/ttft 六类告警
   ↓
输出：卡数 / 台数（8 卡/台）/ 三维分解 / 主导因素 bottleneck / 告警 / 功耗
```

| 关注点 | 文件 |
|---|---|
| 引擎全部公式 | `backend/app/engine/inference.py` |
| 模型结构表（32 个） | `backend/app/catalogs/inference_models.json` |
| 芯片规格表（8 档：910×3 / 950×5） | `backend/app/catalogs/inference_chips.json` |
| 场景档位表（29 档、7 组） | `backend/app/catalogs/inference_scenes.json` |
| 模板加载 | `backend/app/catalogs/inference_catalog.py` |
| 入参校验 | `backend/app/schemas.py` 的 `InferenceRequest` / `InferenceModelInput` |
| 接口 | `backend/app/main.py` 的 `/api/v1/inference/*` |
| 页面 | `frontend/src/InferencePage.tsx`（页面版引擎）+ `BusinessPage.tsx`（业务池接入） |
| 黄金值测试 | `backend/tests/test_inference.py`（938 参数化用例 + 锚点） |

### 11.2 与直观口径的几处关键差异

1. **显存 GiB / 带宽 GB 分工**：权重与 KV 用 `÷1024³`（GiB），权重搬运与带宽时间用 `÷1e9`（十进制 GB）。
   两个口径不能交叉。
2. **KV 双口径**：显存按「每会话分配窗口」（maxCtx 明显大于本轮占用时按窗口写满），
   Decode 带宽按「连续批均值（输入 + 输出/2）」。混用会差一档卡数。
3. **卡数取 max 不相加**：输出是最小卡数；扩容余量不进引擎，由方案 `headroom` 在池层一次放大。
4. **档位缩放指数**：`tier_exponents` 对效率类系数分幅缩放——`mfu_prefill` / `bw_decode` 全额、
   `mem_util` 半幅；`mfu_decode_ratio` 与 `kv_reserve` 不随档位缩放（否则 Decode 会被扣两次）。

### 11.3 经验系数（改这里就等于改结论）

这些值不在代码里，而在 `catalogs/inference_params.json`（`params.current()` 即时合并默认值与覆盖层）。
页面「基线与设置 → 推理参数」可直接改，改完即时生效并落覆盖层。均有出处或明确标注为经验假设：

- `chip_profiles`：按芯片 8 条登记的 Prefill MFU、Decode MFU 比、HBM 带宽利用率、KV 预留、显存容量利用率。
  910B/910C 同族不同档（910C 的 Prefill MFU 0.26 按大 GEMM 达峰口径），950 系列Decode 利用率更高。
- `tiers`：保守 0.8 / 均衡 1.0 / 激进 1.2，配合 `tier_exponents` 指数作用于效率类系数。
- `constants`：12 项任务内部常量（Prefill 预算、Decode 固定开销、M/G/1 排队系数、MoE 填充/饱和、
  FFN 有效利用率上下限、排队利用率上限等）。`tier_exponents` 在参数页只读展示。

### 11.4 已知边界

- 不含 PD 分离形态判定：当前只输出混部结果。PD 分离需要池化收益与 KV 跨池搬运建模，尚未接入。
- 不含芯片单调性审计与三芯对照表：`/inference/estimate` 只算单芯片。
- 不含 TCO 与服务器整机：芯片表里的价格与功耗仅登记，不参与卡数计算。
- 长序列的 KV 衰减与排队时延仍是页面口径的经验近似，与实测可能存在同量级偏差；
  对外报结论须注明依据等级 C 与所用档位。

### 11.6 参数可配置化：改值的正确姿势

```
默认值：backend/app/catalogs/inference_params.json      ← 唯一来源，代码不重复写数字
覆盖层：SQLite kind=inference-params, id=active          ← 页面/接口改的值
生效值：params.current() 即时合并（默认值, 覆盖层）；v2 起不再有 engine.reload()
```

| 想做的事 | 做法 |
|---|---|
| 调某个系数（MFU、KV 预留、余量倍数…） | 页面「推理参数」改 → 保存并生效；或 `PUT /api/v1/inference/params`，body 传要改的字段即可（局部覆盖） |
| 回到出厂值 | 页面「恢复默认」或 `POST /api/v1/inference/params/reset`（清空覆盖层，不动默认文件） |
| 新增一个可调参数 | ① `inference_params.json` 加默认值 ② `params.py` 的 `SPEC`/`TABLES` 登记类型与区间 ③ `inference.py` 在使用处直接读 `params.current()` ④ 前端无需改动（按 schema 自动渲染） |
| 升级默认值且保留用户调参 | 只改 json，不动覆盖层；`_merge` 会让用户改过的字段继续用覆盖值 |

约束：越界值由 `params.validate` 拒绝（返回 422 + 逐字段原因），不做静默截断；
跨字段一致性（MoE FFN 利用率下限 < 上限、Dense 下限 < 1、档位缩放系数 > 0）
在 `_coherence` 里统一校验。

**验证参数影响的坑**：`calculate()` 有 `input_hash` 缓存，payload 没变时重算会命中旧快照，
看起来像「参数没生效」。要在端到端里验证，改用 `POST /inference/estimate`（不缓存），
或让 payload 真的变化一次。`e2e/inference-params.spec.ts` 走的是前一种。

### 11.7 算力命名口径（v1.3.2）：单位与精度基准必须分开

| 想表达 | 正确写法 | 错误写法 |
|---|---|---|
| 某个算力数值 | `5.00 P`、`163 T`、`0 T` | ~~`5.00 P16`~~、~~`163 T16`~~ |
| 该数值的精度基准 | `BF16 基准`、`FP16 基准`、`FP8 基准` | ~~`P16`~~、~~`P16 等效`~~ |
| 两者同时出现 | 列标题「需求算力（BF16）」+ 数值 `5.00 P` | 「需求算力 5.00 P16」 |

- 单位定义：`1 T = 10^12 FLOPS`，`1 P = 1000 T = 10^15 FLOPS`。P / T 只是量级，与位宽无关。
- 当前基准是 **BF16 稠密**（`inference_chips.json` 只登记 `bf16_tflops`）；选 FP16 权重时复用同一算力档，选 FP8 / INT8 用 `int8_tflops`，选 INT4 用 `int4_tflops`，再折回 BF16 与卡容量对齐。
- 代码落点：`frontend/src/api.ts` 的 `capacity()` 只产出数字 + `P` / `T`；`backend/app/derivations.py` 的 `step(unit=...)` 只写单位，精度写进公式或 note。
- 新增展示位时：**列标题负责标精度**，**数值负责标量级**，不要在数值后面续写精度。
