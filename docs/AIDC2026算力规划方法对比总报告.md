# 第一部分　AIDC 算力规划方法整体

## 1.1 站点结构：一条 TCP 因果链

`ai-dc-design.html` 本身是 Tab 容器，九个页签均为 iframe 子页，构成一条从业务到一度电的完整链路：

| 环节 | 页签 / 子页 | 回答的问题 |
|---|---|---|
| 方法论 | Token→Card→Power（`ai-dc-tcp.html`） | 三段公式如何串起来 |
| **算力** | **算力估算（`ai-dc-computeEst.html`）** | **要多少张卡** |
| 设施 | 机柜规划（`aidc-layout-Card2Power.html`） | 多少机柜、多少功率、多少面积 |
| 设施 | 机房布局 / 立体 / 案例 A / B | 平面怎么排、风冷还是液冷 |
| 部署 | 产品协同（`ai-dc-deployment-perf.html`） | 部署形态与性能 |
| 经济 | Investment ROI（`aidc-investment-roi.html`） | 投多少钱、单 Token 成本、能否打平云价 |
| 训练 | 后训练（`post-training.html`，独立页） | 微调数据/训练/评测流程 |

链路：**Token（业务量）→ Card（卡数）→ Power（机柜/电力/制冷/面积）→ ROI（投资与单 Token 成本）**。三段各自独立成式，可正算也可反算（ROI 页支持按机房功率倒推卡数）。

## 1.2 算力估算的完整公式

页面自己在「计算公式与口径」区列出四组公式：

```
公式一  U0    = DAU × R0
        Tuser = Tout + Tin × (1 − H)          H = 缓存命中率，只折减输入侧
        Td    = U0 × Tuser                    全网日均 Token

公式二  Ts    = Td ÷ 24 ÷ 3600                秒级吞吐
        C理论 = Ts × F × Pact × M ÷ N
        n算力 = ⌈ C理论 × Kcompute ÷ Ccard ⌉

公式三  nmin  = ⌈ Ptotal × Bw ÷ (Vcard × η) ⌉  显存部署下限
        ncard = max( n算力 , nmin )

公式四  C未来 = C规划 × (RN ÷ R0) × Kfreq × KAgent
        Kfreq(y) = Kfreq^(y/Nyear)，KAgent(y) = KAgent^(y/Nyear)
        整机台数 nunit = ⌈ ncard ÷ Qunit ⌉
```

下游（机柜规划页）：

```
n_rack = ⌈ n_card ÷ Q_rack ⌉ × K_IT
P_IT   = Σ ( n_rack,i × P_rack,i )
P_机房 = P_IT × PUE          液冷 1.2 / 风冷 1.5
S_IT   = n_rack × K_rack × A_rack
```

> 「本工具用于规划阶段一级匡算，未计入 Prefill / Decode 分离、并发与时延 SLO 及长序列注意力开销。」

# 第二部分　本项目算力规划方法整体

## 2.1 三池架构

| 池 | 计量起点 | 换算方法 | 输出 |
|---|---|---|---|
| **业务场景池** | 并发会话数 + 单请求 IO + TTFT/TPOT | A/B/C 三维约束 → 混部抬升 → SLA 回验 | 物理卡数 + 需求算力（P，BF16 基准） |
| **创新服务池** | 月度 Token 配额 | llm-phases（分阶段 FLOP ÷ η） | 需求算力（P，BF16 基准）（**不出卡数**） |
| **开发测试池** | 微调数据量 × 轮数 | LoRA 工作量 ÷ 训练时限 ÷ η_train | 容量（P，BF16 基准）（槽位聚合） |

三池**各自独立保资源、容量不共享**，汇总时余量只在池层乘一次（`plan.headroom` 默认 0.20）。

## 2.2 业务场景池：A/B/C 三维引擎

```
输入：模型结构（32 预设 + 自定义）· 量化三轴 W/A/C · 场景模板（6 档）
      · 芯片（910B/910C/950 六档）· 并发会话数 · TTFT/TPOT · 敏感度档

① 显存 A：权重装载下界 + KV 需求 → 枚举 TP×PP×EP×DP → 取总卡数最小解
② Prefill B：吞吐卡数 vs 首 Token 时延卡数 → max（机内 8 卡封顶）
③ Decode C：带宽卡数 vs 吞吐卡数 vs A2A 卡数 → max
   ↓ 物理下界 = max(A,B,C)
④ 混部校验：U_pf + U_dc > 阈值(1.03/1.05/1.10) → 按超出比例抬升下界
⑤ SLA 回验：预测 TTFT/TPOT → 不达标逐级加 DP → DP 无效则放大 TP
   ↓
输出：推荐卡数 · 拓扑 · 扩容余量 · 服务器台数 · 瓶颈标注 · 需求算力（P，BF16 基准） · 等效算力（P，BF16 基准）
```

三条口径铁律：**卡数与算力（P）不同量纲**；**余量只在池层乘一次**；**三维取 max 不相加**。

## 2.3 创新服务池：llm-phases

```
Q_month = users × quota_per_user_month × usage_ratio
Q_model,m = Q_month × share_m，Σshare_m = 1
T = service_days × service_hours_per_day × 3600        默认 22×8h

λ_m = Q_model,m ÷ T × peak_factor ÷ request_total_tokens
Li = Breq × β      Lg = Breq × (1−β)                     β 默认 0.8
Fp = 2×Np×Li×κp   Fd = 2×Nd×Lg×κd                       κ = 1.2 MoE / 1.1 Dense
C_m = λ_m × (Fp/ηp + Fd/ηd) ÷ 1e15                        ηp=0.35 ηd=0.15
C_pool = ΣC_m × (1 + headroom)
```

## 2.4 开发测试池

```
F_train = k × N_active × D × E
C_train = F_train ÷ (H × 3600 × ηtrain × 1e15)          k=4 ηtrain=0.25
聚合：C_dev = train_slots × max(各模型 C_train)          只含微调，不含评测
```

# 第三部分　对比一：AIDC 方法整体 vs 本项目整体

## 3.1 层级对位（最重要的结论）

**两者不在同一层级，不是替代关系。**

| 层级 | AIDC | 本项目 |
|---|---|---|
| 业务量建模 | 强（DAU/渗透/Tin/Tout/缓存命中/Agent 放大） | 中（并发会话 + 场景模板 6 档） |
| 单场景容量计算 | **弱**（不分阶段、无并发、无 SLO） | **强**（三维约束 + 混部 + SLA 回验 + 拓扑择优） |
| 多池资源组织 | 无 | **强**（业务/创新/开发三池独立） |
| 多年增长规划 | **强**（RN×Kfreq×KAgent 逐年展开） | 无（v1.1 起主动删除） |
| 设施层（机柜/电力/面积） | **强**（n_rack → P_IT → PUE → S_IT） | 无 |
| 经济层（CAPEX/OPEX/单 Token 成本） | **强**（含云价对照、按功率反算） | 弱（仅加速卡购置） |
| 可审计可复现 | 弱（无快照，改参数即丢失） | **强**（SQLite 快照 + hash 幂等 + 版本比较） |

一句话：**AIDC 是自上而下的战略匡算工具，本项目是自下而上的交付级规划工具。**

## 3.2 相同点（10 项）

| # | 共同做法 | AIDC | 本项目 |
|---|---|---|---|
| 1 | 起点是业务量不是卡数 | DAU×渗透×人均日均 Token | 并发×IO 长度 / 月度配额 |
| 2 | 算力看激活参、显存看总参 | Pact 定算力、Ptotal 定显存 | `_traffic_gb` 用 total、`active_b` 定 FLOPs |
| 3 | 每 Token FLOP = F×激活参 | F=2，引 Kaplan 2020 | `ffn_flops = 2×Pact×1e9×rl` |
| 4 | MFU 式综合利用率打折 | N=45%，引 PaLM | `mfu_prefill` × 衰减曲线 × 0.72 |
| 5 | 显存下限取大避免装不下 | `max(n算力, nmin)` | `n_memory = max(weight_min, unit, total)` |
| 6 | 冗余系数单次乘 | Kcompute=1.2 | MARGIN_FACTOR / headroom=0.20 |
| 7 | 输出含冗余卡数与整机台数 | 主卡数 / 含冗余 / nunit | `cards` / `cards_planned` / `servers` |
| 8 | 精度分档 | FP16/FP8/FP4 三档 | W/A/C 三轴独立，910B/C 无 INT4 强制降 INT8 |
| 9 | 参数显式化、可改、有出处 | 页内公式区 + 4 篇学术引用 | `inference_params.json` + 覆写层 + 越界拒绝 |
| 10 | 声明是估算、需实测校准 | 「一级匡算」 | `evidence_grade=C`、`latency_status=UNVERIFIED` |

## 3.3 核心差异（6 条）

### D1 负载量纲（最根本）

| | AIDC | 本项目 |
|---|---|---|
| 输入 | 日均 Token 总量 + 峰值倍数 M | 并发会话数 + 单请求 IO + TTFT/TPOT |
| 卡数由什么决定 | **吞吐** | **显存 + Decode 单步带宽地板** |
| 时间维度 | 日均 → 秒级均摊 → 峰值放大 | 单请求 E2E 与并发同时约束 |

后果：**两边数字不能直接比**。AIDC 的 1024 卡与业务池的 16 卡放在一张表里会误导。

### D2 阶段拆分

AIDC 把整个前向过程视为一次 `F×Pact`，Prefill 与 Decode 混算，**注意力开销完全不计**。
本项目拆三段：Prefill 单独积（含 `2/4×L×heads×dim×newtok×span`），Decode 单独积，各自取卡数再 max。

### D3 并发与时延

AIDC 只有 M 一个峰谷补偿，无并发、无 SLO。
本项目有排队残余、槽位等待、双 SLO 双向回验、9 轮 E2E 自洽迭代。

后果：本项目**小并发时卡数由显存与带宽地板决定**，与吞吐几乎无关。

### D4 KV Cache

AIDC 完全不计 KV，显存下限只算权重。
本项目 KV 是并发容量的核心：MLA/GQA/MHA 三型 + mean/p90/full 三档 + 带宽随序列衰减（MoE 斜率 0.16/地板 0.70）。

### D5 拓扑与部署形态

AIDC 只有 Qunit 用于折算整机，不选 TP/PP/EP/DP，不判 PD 分离。
本项目完整枚举拓扑择优，混部利用率抬升是唯一形态修正（引擎内无独立 PD 分离判定）。

### D6 增长与下游

AIDC 有完整增长规划与设施/经济层。本项目主动不做增长外推，也没有机柜/电力/面积/OPEX。

## 3.4 同一模型同一卡的数值对照

# 第四部分　对比二：AIDC vs 创新服务池

## 4.1 结论：数学同构，口径不同

**创新池比业务池更接近 AIDC**：业务池与 AIDC 是结构不同的两套方法；创新池与 AIDC 是**同一个数学结构，只是系数与时间基准不同**。

## 4.2 公式对照

| 环节 | AIDC | 创新池 | 关系 |
|---|---|---|---|
| 业务量起点 | `Td = U0 × Tuser`（日均） | `Q_month = U × q × usage_ratio`（月度） | 同构（日 vs 月） |
| 时间基准 | `Ts = Td ÷ 86400`（自然日） | `λ = Q ÷ T ÷ Breq`，T = 22×8×3600 | **不同（关键）** |
| 峰值补偿 | `M` = 3 | `peak_factor` = 3 | **完全相同** |
| 单 Token 算力 | `F × Pact`，F=2 | `2×Np×κp` + `2×Nd×κd` | 结构同，κ 为差异 |
| 效率 | `N` 单一（coding 场景 45%） | `ηp=0.35 / ηd=0.15` 分阶段 | **不同** |
| 卡数 | `⌈C×K ÷ Ccard⌉` | **无此步** | **缺失** |
| 显存下限取大 | `max(n算力, nmin)` | 仅费用附录做，主链路不做 | **不同** |
| 冗余 | `Kcompute=1.2` | `headroom=0.20` | 几乎相同 |
| 配额使用率 | 无（隐含 100%） | `usage_ratio` 可调 | **创新池独有** |
| 模型份额 | 单模型 | `share_m`，Σ=1，各模型峰值同时发生 | **创新池独有** |

## 4.3 逐项对齐验证（核心证据）

固定输入：300 人 × 100 万 token/月，Qwen3.6-35B-A3B（MoE，3B 激活），单模型 100% 份额，peak=3，Breq=2560，β=80%，ηp/ηd=0.35/0.15。

| 步骤 | 创新池 PF | AIDC PF | 残差 |
|---|---|---|---|
| 起点（22×8h，κ=1.2，η 分阶段） | 0.037013 | 0.004630 | **7.9948** |
| ① 时间基准改为自然日 30×86400 | 0.009048 | 0.004630 | 1.9543 |
| ② 再去掉 κ（1.2→1.0） | 0.007540 | 0.004630 | 1.6286 |
| ③ 效率统一为单一 0.45 | 0.004630 | 0.004630 | **1.0000** |

**残差精确收敛到 1.0000，不是巧合，是同一个数学结构。**

## 4.4 差异的精确分解

```
7.9948 = 4.0909 × 1.20 × 1.6286
         时间基准   结构修正   效率口径
       = (2592000 ÷ 633600) × κ × (0.45 ÷ 0.2763)
```

其中 `0.2763 = (Fp+Fd) / (Fp/0.35 + Fd/0.15)` 是两阶段效率的**谐波等效值**。

| 项 | 倍数 | 物理含义 |
|---|---|---|
| 时间基准 | **4.0909** | 整月额度压进 22×8h 工作时段 vs 自然月均摊 |
| 结构修正 | **1.20** | κ=1.2 补路由/门控/归一化等额外开销；AIDC 无此项 |
| 效率口径 | **1.6286** | 分阶段 η 谐波等效 0.2763 vs AIDC 单一 0.45 |
| **合计** | **7.9948**（MoE）/ **7.3286**（Dense） | — |

**与规模、模型、请求长度、峰值倍数全部无关**（3/300/3000 人比值恒为 7.995；512~8192 token 请求长度比值不变）。

### 能改变比值的两个参数

`η_equiv = (β + (1−β)·Nd/Np) / (β/0.35 + (1−β)·Nd/Np/0.15)`，Breq 在分子分母约掉。

| β（输入占比） | η_equiv | 总比值 |
|---|---|---|
| 50% | 0.2100 | 10.52 |
| **80%（默认）** | **0.2763** | **7.99** |
| 90% | 0.3088 | 7.15 |
| 100% | 0.3500 | 6.31 |

| 服务窗口 | 窗口秒数 | 与自然日之比 | 总比值 |
|---|---|---|---|
| 5 日 × 8h | 144,000 | 18.0 | 35.18 |
| 7 日 × 12h | 302,400 | 8.57 | 16.75 |
| **22 日 × 8h（默认）** | **633,600** | **4.09** | **7.99** |
| 22 日 × 24h | 1,900,800 | 1.36 | 2.67 |
| 30 日 × 24h | 2,592,000 | 1.00 | 1.95 |

## 4.5 结构性缺口（比系数更重要）

| 缺口 | 说明 |
|---|---|
| ~~**① 主链路不出卡数**~~ | **已修（v1.4）**：`pools[].cards` 已输出，口径见第五部分 P0 |
| ② 显存不参与取大 | AIDC 有 `max(n算力, nmin)`，创新池主链路 BF16 合计算力完全不看显存 |
| ③ 显存算法粗 | `memory_gb ÷ card.memory_gb`，未考虑 TP 切分与 KV 容量约束并发 |
| ④ 无卡型选择 | Ccard 只在费用附录用 `dense_p16`，主链路不涉及芯片 |
| ⑤ 无拓扑/SLA/增长 | 与 AIDC 同为缺失，双方都需要补 |

实测（Qwen3.6-35B-A3B，β=80%）：

| 用户数 | base_p | planned_p | 显存 GB | compute_cards | memory_cards | reference_cards |
|---|---|---|---|---|---|---|
| 300 | 0.0370 | 0.0444 | 97.4 | 1 | 2 | 2 |
| 3,000 | 0.3701 | 0.4442 | 134.9 | 1 | 2 | 2 |
| 30,000 | 3.7013 | 4.4416 | 510.7 | 10 | 6 | 10 |

**300 人与 3,000 人参考卡数完全相同（都是 2 卡）**——96GB 卡上显存约束封顶，且 `memory_status` 恒为 PROXY，`reference_cards` 实为下界。

## 4.6 创新池独有的两个机制

1. **`usage_ratio` 配额使用率**：AIDC 隐含额度 100% 兑现，创新池可显式建模"实际只用 60%"。
2. **多模型 Token 份额守恒**：`Σshare_m = 1`，各模型峰值同时发生。AIDC 是单模型，无法表达"一个配额池按份额分给多个模型"。

这两点是创新池相对 AIDC 的真实增强，不是缺失。

# 第五部分　结论与建议

## 5.1 三个结论

1. **AIDC 与本项目整体不在同一层级**：AIDC 强在业务建模、增长规划、设施与经济层，弱在单场景容量计算；本项目正好相反。两者是互补，不是替代。
2. **AIDC 与创新池数学同构**：把三处差异拉回后残差精确为 1.0000。8 倍差距是口径选择（时间基准 4.09×、κ 1.2×、效率 1.63×），不是方法对错。
3. **业务池是唯一同时具备「三维约束 + 并发/SLA + 卡数输出」的方法**，也是本项目相对 AIDC 的核心竞争力所在。

## 5.2 建议（按优先级）

### P0：修创新池的卡数缺口 —— **已完成（v1.4）**

原状态：用户填完创新池看不到卡数，卡数只在费用附录出现。

已实现（`calculator.cards_for_pool`）：

```
n_compute = ⌈planned_p × 1000 ÷ chip.bf16_tflops⌉          算力卡数
n_memory  = ⌈memory_gb ÷ chip.memory_gb⌉                  显存卡数
n_card    = max(n_compute, n_memory)                      AIDC 的取大逻辑
cards_planned = max(n_card + 1, ⌈planned_p×(1+h)÷chip⌉)    按余量放大且至少多一张
servers   = ⌈n_card ÷ 8⌉
capacity_p = n_card × chip.bf16_tflops ÷ 1000             等效算力（P，BF16 基准）
```

关键设计决定：

1. **芯片与业务池共用** `catalogs/inference_chips.json`（`Innovation.chip_key` 默认 910C），否则两池卡数不可比。
2. **池层不对齐整机**。业务池按单实例卡数对齐是因为要给出可部署拓扑；池层混机型，按 8 卡对齐会把「1 卡」放大成「9 卡」。
3. 芯片缺失时 `cards=null` 并给 `cards_detail.reason`，不按默认芯片硬算。
4. 字段名与业务池一致（`cards / cards_planned / servers`），推导过程在 `cards_detail`。

实测（Qwen3.6-35B-A3B / 910C / β=80% / 余量 20%）：

| 用户数 | planned_p | 算力卡数 | 显存卡数 | 卡数 | 含余量 | 瓶颈 |
|---|---|---|---|---|---|---|
| 300 | 0.0444 | 1 | 1 | 1 | 2 | 持平 |
| 3,000 | 0.4442 | 1 | 2 | 2 | 3 | 显存 |
| 30,000 | 4.4416 | 8 | 4 | 8 | 10 | 算力 |

### P1：统一两池的显存口径

业务池 `_enumerate_memory` 枚举拓扑、反解 KV 容量；创新池直接相除。同一方案里两套算法会被质疑。建议创新池补主链路时统一到业务池口径。

### P2：修业务池并发非单调（正确性问题）—— **已完成（v1.4.1，2026-11-10）**

`inference.py` 在并发跨过 `MAX_NUM_SEQS=256` 后卡数非单调下降：

```
224 并发 → 128 卡，floor=12，DP8，TPOT 43.6ms，SLA 达标
256 并发 →  32 卡，floor=16，DP2，TPOT 53.1ms，SLA 不达标
```

当时的定位（`eff_bsz_all` 单点封顶 vs `kv_need_gib` 全量口径）只是第一层；
深挖后发现根因是四层叠加：① 有效批与 KV 全量口径矛盾；② SLA 回验路径依赖
（显存枚举器跨档切换拓扑后，旧拓扑堆出的 DP 不回收）；③ 部署惩罚分泄漏进
`n_memory` 卡数下界（48↔40 卡互换）；④ 等卡数方案无平局打破。

修复：SLA 回验重写为「全拓扑最小满足 dp 搜索」，`eff_bsz_all` 全量口径，
`n_memory` 改用枚举器 `min_total`，等卡数按单步时延打破平局。
专项扫描 32 模型 × 6 芯片 × 5 场景 × 64 并发点 = 61440 次评估，违例 0；
回归测试 `test_cards_monotonic_*` 五项长期守护。详见 `docs/更新记录.md` v1.4.1。

### P3：口径开关（仅对外对齐时做）

若需要复现 AIDC 数字，三个可选开关：`time_basis`（service_window / calendar_month）、`structural_kappa`（1.2 / 1.0）、`efficiency_model`（split / single）。**不建议改默认值**——创新池现有的保守口径是它相对业务池的互补价值所在。

### P4：设施与经济层（视交付需要）

若要对外做机房/投资级交付，需补 `n_rack`、`P_IT`、`PUE`、`S_IT` 与 CAPEX/OPEX。需要机柜规格库与 PUE/电价基线，工作量最大。

## 5.3 对外汇报的注意事项

- **绝不能直接摆「1024 卡 vs 16 卡」**：负载量纲差两个数量级，直接对比会误导。
- 引用 AIDC 数字时必须同时说明：场景 DAU、人均日均 Token、峰值倍数、N=45%。
- 引用本项目数字时必须同时说明：用的是哪一档敏感度（乐观/中性/保守同一输入差 15%~30%）。
- 创新池当前只给算力（P），若要报卡数必须说明来自费用附录、且是下界。
