估算方法说明

从场景参数到卡数的完整计算链路（5 步）；展开任一场景的「计算过程」即杜邦式逐层拆解，可从总卡数一直下钻到原始参数

推理服务不是「总算力 ÷ 有效算力」的单维估算：显存装不装得下、首 Token 时延达不达标、逐 Token 生成够不够快，是三条互相独立的约束。本页对每条约束分别求出满足条件的最小卡数，取三者最大值作为单场景结果；主导因素会随并发与时延目标在三者之间转移，因此三步都要算，不能只看其中一步。

输入与全局配置：把业务描述折算成计算参数

选场景类型会带出该场景的输入长度、输出长度、并发数、TTFT/TPOT 目标（也可点「调整参数」手动改）。全局三项配置决定硬件与效率口径：算力卡给出峰值算力、单卡显存与 HBM 带宽；W/A/C 三轴量化分离——权重精度定显存装载量、激活精度定峰值算力档位、KV 精度（自动跟随）定并发容量；工程开销档位只缩放「效率类」系数（Prefill MFU、Decode 带宽利用率全额，单卡显存利用率半幅；保守 ×0.8 / 均衡 ×1 / 激进 ×1.2），结构性开销与口径常数不受档位影响，可展开看各项生效值。若预设型号不适用，可在算力卡下拉选「自定义算力卡」按厂商规格填写峰值算力、显存、带宽、互联与功耗，计算链路完全一致。

理论依据：MFU（算力利用率）的度量口径见 PaLM（arXiv:2204.02311）；显存利用率与 KV 预留沿用 vLLM / PagedAttention 的可用显存划分方式（arXiv:2309.06180）；W / A / C 三轴量化档位为工程实践归纳，非单一文献结论。详见下方 估算依据。

A · 显存约束：模型装得下，KV 放得开

显存看总参、算力看激活参：MoE 模型推理要把全部专家装进显存（按 1.08 偏斜系数放大），计算时只激活少量专家。权重装载宽度按 2 的幂取 TP（机内上限 8 卡），权重超单机则按 8 的倍数跨机对齐（EP/PP）。KV Cache 按连续批均值预留，不是每路写满上下文窗口：每 token KV 由注意力结构决定（GQA 按 KV 头数折算、MLA 按低秩 latent，可压缩约一个量级）。若权重恰好装满导致 KV 房间为 0，自动提升装载宽度。

理论依据：显存构成（权重 + KV + 激活峰值）与 KV 分块管理见 vLLM / PagedAttention（arXiv:2309.06180）；KV 每 token 的 GQA 折算见 arXiv:2305.13245，MLA 低秩折算见 DeepSeek-V3 技术报告（arXiv:2412.19437）；1.08 专家偏斜系数与 90% 显存利用率为工程经验值。

B · Prefill 约束：首 Token 时延（TTFT）达标

按稳态到达率 λ = 并发 ÷ 单请求时长（请求时长 = TTFT + 输出 × TPOT）估吞吐，每请求 Prefill FLOPs = GEMM（2 × 激活参 × 输入 ÷ FFN 有效利用率）＋ 注意力项（4 × 层数 × 注意力宽 × 输入 × 有效跨度，MLA 按 QK/V 完整头维计，低秩压缩只省 KV 缓存不省计算）。FFN 有效利用率随 token 规模爬升：MoE 看「每专家平均分到的 token 数」，Dense 看 prompt 长度——短 prompt 的矩阵乘填不满，只跑出四到五成效率。吞吐与排队双约束：吞吐给出持续处理能力下限 N1；再逐卡数枚举服务时间＋M/G/1 排队等待，找到 TTFT ≤ 目标的最小卡数 N2（利用率 ρ ≥ 1 判为饱和、需加卡）。排队不能忽略，高并发下 TTFT 主要由等待时间主导。

理论依据：连续批处理下的到达率与服务时间模型见 Orca（OSDI 2022）与 Sarathi-Serve（arXiv:2403.02310）；排队等待按 M/G/1 近似（Kleinrock《Queueing Systems, Vol.1》）；每 token FLOPs ≈ 2 × 参数量 的算法见 kipp.ly（Transformer Inference Arithmetic）。

B · Prefill 约束
单请求 FLOPs
2 × 激活参 × 输入 ÷ FFN 有效利用率　＋　4 × 层数 × 注意力宽 × 输入 × 有效跨度
FFN 有效利用率：MoE 0.07 + 0.43 × (1 − e^(−每专家token/800))（封顶 0.7）；Dense 0.42 + 0.58 × (1 − e^(−输入/5500))。MLA 的注意力宽 = 头数 × (QK头维 + V头维) ÷ 2
吞吐下限 N1
ceil( λ × FLOPs/请求 ÷ (单卡有效算力 × 0.85) )
0.85 为持续负载余量
时延下限 N2
TTFT(N) = 服务时间(N) + 排队等待(ρ)
枚举 N，取 TTFT(N) ≤ 目标 的最小值
结果
B = max(N1, N2)
4

C · Decode 约束：逐 Token 时延（TPOT）达标

Decode 是带宽游戏：每生成一个 token 都要把激活权重从显存读一遍，单步耗时取「计算时间」与「权重读取时间」的较大者；MoE 只读取命中的专家权重。枚举「TP 分片宽度 × 副本数」组合，取满足 TPOT 目标的最小总卡数。若目标严于理论下限（权重读取 ÷ HBM 带宽 + 固定开销），页面会给出「加卡无效」告警——此时应换更高带宽的卡或放宽时延目标，而不是继续加卡。

理论依据：Decode 每步需读取激活权重、TPOT 受显存带宽约束的推导见 kipp.ly（Transformer Inference Arithmetic）；混合批中 Prefill 抢占导致的 Decode 时延抖动见 Sarathi-Serve（arXiv:2403.02310）对 chunked-prefill 的动机分析；0.4 重叠惩罚与 1.35ms 调度开销为工程经验系数。

C · Decode 约束
单步耗时
max( FLOPs/步 ÷ 分片有效算力, 权重字节 ÷ (分片 × HBM 带宽 × 利用率) ) + 固定开销
理论下限
权重字节 ÷ (带宽 × 利用率) + 固定开销；目标更严 → 告警
结果
C = 满足 TPOT 目标的最小「分片宽度 × 副本数」

合成与汇总：取最大、对齐、求和

当前按「混部」方式估算：Prefill 与 Decode 共用同一批卡，因此单场景卡数取 max(A, B, C)——同一批卡同时要装下权重与并发 KV、要满足 TTFT、要满足 TPOT，三者取最紧的一条。若实际采用 PD 分离（Prefill 池与 Decode 池各自独立、卡数相加，两池各装一份完整权重），总卡数会高于这里的混部口径；本工具暂不区分这两种部署方式，混部口径也未单独计入 Prefill 尖峰对 TPOT 的干扰（该影响已折入 B 的计算预算占比与 C 的重叠惩罚两项系数）。单场景卡数还要奇数补偶，跨机按 8 的倍数对齐；页面行内标注最大者对应的主导因素（显存 / Prefill / Decode）。多场景按芯片型号分组求和（不同芯片不混算），算力汇总区给出总卡数与服务器台数（功耗不在页面汇总，单卡功耗仅在算力卡信息中展示）。本页只输出算力需求量：故障冗余、业务突发等采购侧预留不在工具内计算，需要时请在本结果之上按 SLA 另行加余量（如 N+1、多买一台，或按比例上浮）。每个场景行点「▸ 计算过程」可看到 A/B/C 三块公式代入当前具体数字的结果，逐步可复算。

理论依据：三条约束取最大值是混部部署（同一批卡同时承担 Prefill 与 Decode）的容量口径，无公开标准，属工程口径；服务器台数按 8 卡/台折算（不同芯片不混机）；算力需求量为「恰好满足 SLA 的最小卡数」，不含故障冗余与业务突发——容量规划惯例中的 N+1 / 百分比冗余属采购口径，需在需求量之外另行叠加，故不在本页计算。

口径说明

  • ① 算力口径：表中 FP16 / FP8·INT8 / MXFP4 均为官方「Cube + Vector 总算力」。官方同表另给「仅 Cube」矩阵算力（950PR 32/28 Cube：FP16 432/378T、FP8·INT8 865/756T；950DT 36/32/28 Cube：FP16 486/432/378T、FP8·INT8 973/865/756T）。本工具按总算力估 MFU，若做纯矩阵算力对拍，需按仅 Cube 口径折减。全联接大会 2025 公布的 950 系列 FP8 1P / FP4 2P 为芯片峰值天花板（徐直军主题演讲 ↗），低于表中满配档的 919T / 1784T，属不同统计口径，勿混用。
  • ② 五档与实物的对应：官网处理器页按 Cube Core 数量给出 32/28（PR）与 36/32/28（DT）五档，已公开整机/标卡各自对应其中一档——Atlas 350 = PR-28、Atlas 650E = DT-28、Atlas 850E = DT-32；不存在「整机标称只有一个值」的说法，此前仅取 425T/804T 是把最低档当成了全系代表。
  • ③ 互联带宽统一取芯片级单向等效值（官方双向标称 ÷2）：910B 196（64GB/32GB 两档相同，800I A2 整机 8 卡全互联 392 双向）、910C 392（800I A3 页 D2D 双向 784GB/s ÷2）、950 系列 1000GB/s（灵衢 2.0 最大 2TB/s 双向）。Atlas 350 标卡的卡间灵衢连接器为 424GB/s（双向），按标卡组网时可在自定义卡中填 212。
  • ④ 功耗：910B 64GB 档 300W、32GB 档（Atlas 300T A2 标卡）350W，910C 600W，均取板卡级公开值；950PR 取标卡 ≤600W；950DT 官方只公布整机功耗（650E 14.5kW、850E 15.6kW，含 2×鲲鹏 950 与风扇），扣公共部件后单卡按 0.90 / 0.95 / 1.00kW 工程估算，36 Cube 满配取 1.00kW。
  • ⑤ 显存配对（未决项）：《昇腾950 NPU架构白皮书》表 3-1 给出 DT 支持 144GB / 96GB，但未把 36/32/28 Cube 与容量逐档绑定。本工具按已公开整机配置配对（满配 144GB ↔ 36 Cube，96GB ↔ 32/28 Cube），订货请以官方配置表为准；官网处理器页另列 PR 84GB 容量档，未作为独立 SKU，需要时走「自定义算力卡」。
  • ⑥ 「核」的口径：档位数字是芯片内 Cube Core（3D 矩阵运算核）的个数，Vector Core 数为 2 倍（32/64、28/56、36/72）——它不表示 CPU 核数，也不表示整机的服务器 CPU 配置。做纯矩阵算力对拍时看「仅 Cube」一列；本工具的算力/显存/带宽取值与核数无关，只按档位整体标称，改动档位不会影响计算链路。
  • ⑦ 选卡建议：950PR 偏 Prefill（1.6TB/s、128GB，算力密度最高），950DT 是「以带宽换容量」（4.0TB/s、96/144GB），Decode 带宽下限与 TPOT 敏感场景更占优；长上下文、大权重这类显存主导场景仍可能更吃卡，选档时优先看显存而不是标称算力。
  • ⑧ 910 家族与 950 的差异：950 官方逐档给规格，故 5 档全列；910B 官方只给整机 / 标卡标称（Atlas 800T A2 整机 2.24 PFLOPS ÷ 8 = 280T/卡），4 个型号中只有 20 Cube 档有公开标称，24 Cube 的 B1/B2 未逐型号公开算力（第三方测算 376 / 414T，主要用于液冷 Atlas 900T A2），故未写进预设、需要时走自定义卡，避免把未核验数字当成官方规格。910C 为单款单档：本工具取推理整机口径 560T（Atlas 800I A3 整机 4.48 PFLOPS ÷ 8 颗 NPU），显存 128GB、带宽 3.2TB/s、D2D 784GB/s 双向均取自该页技术规格表；官网另有超节点整机 6.0 PFLOPS ÷ 8 = 750T 与芯片标称 800T，属不同交付形态 / 统计口径，按那一口径估算时在自定义卡填 750 / 800 重算即可，勿与预设值混用。
